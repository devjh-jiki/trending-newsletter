# Daily/Weekly 상세 뉴스레터 형식 개편 설계

## 배경

현재 daily와 weekly 뉴스레터는 GitHub Trending의 짧은 설명만 LLM에 전달한다. 생성 결과에는 직군별 추천과 Quick Start가 포함되지만, 레포의 성격과 실제 활용 방식을 판단하는 데 필요한 근거와 설명은 부족하다. Discord 알림은 상위 5개 레포의 한 줄 설명만 보여 주고, 자세히 보기 링크에서도 직군별 추천과 Quick Start를 강조한다.

## 목표

- daily와 weekly에서 직군별 추천을 완전히 제거한다.
- Quick Start 및 `바로 써보기` 섹션을 완전히 제거한다.
- 각 레포의 README를 분석 근거에 추가한다.
- 레포가 무엇인지, 어디에 사용하는지, 도입 전에 살펴볼 점을 구조적으로 설명한다.
- archive와 Discord가 같은 콘텐츠 정책을 사용한다.
- README 수집 또는 LLM 분석이 일부 실패해도 전체 뉴스레터 생성을 계속한다.

## 범위

변경 대상은 새로 생성되는 daily/weekly archive와 Discord 알림이다. 기존 archive는 과거 기록으로 유지하며 다시 생성하지 않는다. 월간 모드는 별도 스케줄이 없지만 공용 렌더링 경로를 사용하므로 제거된 섹션은 동일하게 나타나지 않는다.

## 데이터 흐름

1. 기존 방식으로 GitHub Trending 레포 목록을 수집한다.
2. 각 레포에 대해 GitHub Contents API의 README 엔드포인트를 호출해 기본 README 원문을 가져온다.
3. `GITHUB_TOKEN`이 있으면 인증 헤더에 사용하고, 없으면 공개 API 요청을 사용한다.
4. 레포 메타데이터, Trending 설명, README 전체를 LLM에 전달한다.
5. LLM의 구조화된 결과를 정규화해 archive와 Discord 출력에 공통으로 사용한다.
6. README 조회가 실패하면 Trending 설명만으로 분석한다. LLM 호출이나 응답 파싱이 실패하면 기존 fallback 요약을 사용한다.

## README 처리 원칙

README에는 인위적인 글자 수 또는 문자 수 제한을 두지 않는다. 매우 큰 README는 입력 비용 증가, 모델 컨텍스트 초과, 제공자 요청 실패를 일으킬 수 있다. 이 경우 해당 레포의 LLM 분석 실패 처리 경로를 통해 fallback하며 다른 레포와 전체 발송은 계속한다.

README는 신뢰할 수 없는 외부 데이터다. 시스템 프롬프트에서 README 안의 지시문을 따르지 말고 프로젝트 분석 자료로만 취급하도록 명시하며, 입력에서도 명확한 구분자로 감싼다. README와 Trending 정보에 근거가 없는 기능, 설치법, 성능, 인기 원인은 추측하지 않는다.

## 요약 데이터 모델

기존 `roles`, `recommendReason`, `quickStart` 필드는 제거한다. 레포별 요약은 다음 필드를 사용한다.

- `koDescription`: 원문 설명을 자연스럽게 옮긴 짧은 핵심 설명
- `summary`: 프로젝트의 정체성, 해결하는 문제, 핵심 기능과 작동 방식을 설명
- `useCases`: 실제 적용 분야, 적합한 사용자와 문제 상황을 설명
- `considerations`: README에서 확인되는 제약, 전제 조건, 도입 시 확인할 점. 근거가 없으면 빈 문자열

각 필드는 사실 중심의 자연스러운 한국어로 작성한다. 문장 수나 출력 글자 수는 강제하지 않지만, 같은 내용을 반복하거나 홍보 문구를 답습하지 않는다.

## Archive 출력

상단의 제목, 오늘/이번 주의 흐름, 총 레포 수와 출처는 유지한다. 직군별 추천 섹션은 렌더링 코드와 데이터 모델에서 제거한다.

각 레포는 이름, 링크, 언어, 누적 스타, 기간 내 스타 증가량과 함께 다음 순서로 표시한다.

1. 짧은 핵심 설명
2. `무엇인가` 상세 분석
3. `어디에 쓰나` 활용 분석
4. `살펴볼 점` 도입 고려사항. 값이 있을 때만 표시

Quick Start 및 셸 코드 블록은 렌더링하지 않는다. archive 상세 분석에는 별도의 글자 제한을 두지 않는다.

## Discord 출력

기존처럼 상위 5개 레포와 archive 링크를 한 개의 embed로 보낸다. 각 레포에는 이름, 언어, 스타 정보와 함께 `summary`와 `useCases`의 핵심을 표시한다. 링크 문구는 직군별 추천과 Quick Start를 언급하지 않고 `전체 상세 분석 보기`로 바꾼다.

Discord embed description의 4,096자 제한은 플랫폼 강제 제약이므로 유지한다. 전체 메시지가 제한을 넘으면 기존 `clip` 방식으로 안전하게 축약하며, archive에는 축약되지 않은 분석이 남는다. daily와 weekly는 각각 기존 제목과 `오늘의 흐름`/`이번 주의 흐름` 라벨을 유지한다.

## 오류 처리

- README 404: README가 없는 정상 상태로 보고 Trending 설명만 사용한다.
- GitHub 403, rate limit, 네트워크 오류: 경고 후 해당 레포를 Trending 설명만으로 분석한다.
- LLM 오류 또는 JSON 파싱 실패: 해당 레포에 fallback 요약을 사용한다.
- 일부 레포 실패: 나머지 레포 처리, archive 저장, Discord 발송을 계속한다.
- Discord 발송 실패: 기존처럼 경고만 남기고 archive 생성 결과는 유지한다.

토큰이나 README 원문은 로그에 출력하지 않는다.

## 구현 경계

- README 수집은 별도 함수로 분리해 네트워크 처리와 요약 책임을 구분한다.
- Discord embed 데이터 생성은 테스트 가능한 순수 함수로 분리하고 실제 webhook 전송과 분리한다.
- daily와 weekly를 위한 별도 구현을 만들지 않고 기존 공용 파이프라인을 유지한다.
- README 외 topics, license, homepage 같은 추가 GitHub 메타데이터 수집은 이번 범위에 포함하지 않는다.
- 기존 archive 파일은 수정하지 않는다.

## 테스트와 완료 기준

구현은 실패하는 테스트를 먼저 작성하는 TDD 순서로 진행한다.

- README 조회 성공 시 원문을 반환한다.
- `GITHUB_TOKEN`이 있으면 인증 헤더를 사용하고, 없어도 요청할 수 있다.
- README 404와 기타 조회 오류에서 전체 처리가 중단되지 않는다.
- LLM 입력에 자르지 않은 README와 외부 데이터 구분 지시가 포함된다.
- 새 `summary`, `useCases`, `considerations` 스키마가 누락 필드와 잘못된 타입을 안전하게 정규화한다.
- archive에 직군별 추천, 바로 써보기, Quick Start 코드 블록이 나타나지 않는다.
- archive에 `무엇인가`, `어디에 쓰나`, 선택적 `살펴볼 점`이 올바른 순서로 나타난다.
- Discord에 제거된 기능을 언급하지 않고 상위 5개 상세 요약과 전체 분석 링크를 표시한다.
- Discord 출력은 플랫폼의 4,096자 제한을 넘지 않는다.
- daily/weekly 제목과 흐름 라벨이 유지된다.
- 전체 `npm test`가 통과한다.

README, 워크플로 주석, `package.json` 설명도 새 동작과 일치하도록 갱신한다.
